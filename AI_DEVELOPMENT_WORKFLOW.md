# AI-assisted development workflow

1. Start with `AGENTS.md`, `SESSION.md`, the selected `READY` task in `PROJECT_TASKS.md`, relevant sources/tests, and Git status. Ask for a missing owner decision only after completing independent discovery. Do not repeatedly scan the full repository.
2. Use one active queue. Each task has a bounded objective, explicit acceptance/validation, and a concise Conventional Commit title (`type(scope): description`, with the scope optional). If useful, use one short lowercase scope naming a codebase area; keep the description brief and omit task-ID footers. The queue ID links the work to its task. Include the title in every task completion report, whether or not a commit is made. Move a dependent task to `READY` only after its prerequisite evidence is recorded. Keep local completion separate from hosted or owner acceptance. Archive completed task detail so the live queue stays short; do not invent replacement work when it is empty.
3. Characterize existing behavior with synthetic data, then make a small vertical change. Validate the owning boundary, integration behavior, and applicable release gate. Prefer direct modules and contracts to speculative layers.
4. Route by the task's hardest decision, then use the lowest capable effort:
   - **GPT-6 Luna · Low (`gpt-6-luna`) is the default** for most implementation, tests, refactors with a clear contract, documentation edits, and source extraction. Use **Luna · Medium** for a bounded multi-file fix or debugging step only when Low is insufficient.
   - **GPT-6 Sol · Low (`gpt-6-sol`)** handles architecture choices, cross-layer design, security review, identity, migration planning, and data-integrity analysis when the evidence is straightforward. Use **Sol · Medium** for consequential decisions with conflicting evidence or nontrivial authorization/integrity reasoning.
   - Do not default to Sol · High or route work to Astra. Raise effort beyond Sol · Medium only for a documented, unresolved problem after lower-effort work and deterministic checks are insufficient; explain the reason in the task record. Break a mixed task into scoped Luna implementation and a Sol decision step when that keeps boundaries clear.
   - Record the intended model and effort in the active task and completion report. Record the actual runtime model only when Codex exposes it; editing this file does not switch the model of an active chat. Check the models actually available in the Codex environment at task start. Use deterministic commands for routine validation.
5. Record a consequential choice in `docs/architecture/DECISIONS.md`, a concise handoff in `SESSION.md`, and evidence in the task. Keep secrets and real personal data out of prompts, tests, logs, screenshots and commits. Do not commit automatically or perform owner-operated cloud/destructive actions.

Official [OpenAI model-selection guidance](https://developers.openai.com/api/docs/guides/model-selection) describes Luna · Low for fine-grained edits and Sol · Medium for complex technical work. The current Codex model list includes `gpt-6-luna` and `gpt-6-sol`, both with Low and Medium effort; recheck availability if the environment changes. This project deliberately starts Sol at Low for straightforward architecture/security review and uses Medium only when needed.

Commit format follows [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) and the [scope guidance](https://gist.github.com/qoomon/5dfcdf8eec66a051ecd85625518cfd13#scopes): a scope is optional and describes a codebase area, rather than an issue identifier.
